# Round 2 conservative rework of GaganEA (v2.11) (v1)

Round 2 attacks the three diagnosed failures of the losing v2.10 baseline (41% drawdown, PF 0.62, ~100 trades/day) by cutting per-trade risk 6x, capping simultaneous exposure, throttling entry frequency, disabling the noisier pattern detectors, rebalancing the stop/target ratio, and — most consequentially — turning on three real-stop-loss protection functions (`ApplyBreakevenToTickets`, `ApplyTrailingToTickets`, `ApplyMasterTrailing`) that were defined but never called in the baseline. All edits live in `GaganEA.mq5` plus a Round 2 log entry; no other files changed. The parameter changes are internally consistent and the newly-wired stop-modification code preserves the existing directional guards, so no stop can be moved the wrong way. The main thing to scrutinize is that "dead code becoming live code" is the largest behavioral shift in this diff and it ships two very tight trailing distances whose real-money effect nobody has observed yet.

**Watch for:** the master trailing stop and the after-T2 individual trail both move *real* broker stops now, at 15 points ($0.15) and 30 points ($0.30) respectively on gold — extremely tight, likely to be stopped out on noise (likely); `ApplyMasterTrailing` trails against a *summed* multi-position profit metric that was only ever a close-trigger before (possible); and no MQL5 compiler exists in this sandbox, so all judgments are read-through only.

**Verdict**: APPROVED

## High-level view

The risk and frequency changes are straightforward default swaps and hold together: 1% risk, a hard cap of 2 concurrent positions, a 3-bar entry cooldown, and much wider EMA/stacking distances all push in the same "trade less, risk less" direction, and the entry-suppression logic correctly handles the cold-start (no prior entry) case so it cannot deadlock entries permanently.

The reward:risk rebalance is coherent: targets stay ordered (500/1000/1800), the stop tightened to 1000, and the partial-close ladder (33% / 50% of remainder / 100%) banks a smaller first slice while leaving the majority to run — the intended inversion of "winners smaller than losers."

The consequential change is protection wiring. Three functions that never ran before now issue `PositionModify` calls. The direction guards are intact (a BUY stop only ratchets up, a SELL stop only ratchets down, breakeven only moves toward profit), so the code is safe against moving a stop backwards. The open risk is behavioral, not correctness: the trailing distances are tiny for gold and the master-trail path drives real stops off an aggregate profit figure, so this is where a backtest is most likely to reveal surprises.

### Entry throttling: cap, cooldown, and distance widening

Three independent brakes now gate `OpenTrade()`, evaluated before either side is considered. The concurrent cap reads `open_buy_count + open_sell_count` (refreshed every tick by `CountOpenPositions()`) and returns early at or above `Max_Concurrent_Positions`; the `> 0` guard lets a user disable it by setting 0. The cooldown compares `iTime(_Symbol, Trade_Timeframe, 0)` against `last_entry_bar_time` and requires `Entry_Cooldown_Bars * PeriodSeconds(Trade_Timeframe)` seconds to elapse. The cold-start case is handled correctly: `last_entry_bar_time` initializes to 0 and the cooldown block is skipped while it is 0, so the very first entry is never blocked and entries cannot deadlock permanently. `last_entry_bar_time` is set only *after* a successful `trade.Buy()`/`trade.Sell()`, so a rejected order does not arm the cooldown.

The distance widening (`Min_EMA_Distance` 150→400, `Min_Trade_Distance` 20→500) is measured in raw `_Point` in both `OpenTrade()` and `DistanceCheckOK`, so the new values mean ~$4 extension from the EMA and ~$5 separation between stacked entries — a real gap versus the old ~$0.20. The cap bounds exposure, the cooldown bounds frequency, and the distance filters bound entry quality; combined they make the old "~100 trades/day" regime structurally impossible.

### Reward:risk rebalance

The partial ladder in `ManageTargets` closes `T1_ClosePercent` (33%) at T1, then `T2_ClosePercent` (50%) of the *remaining* volume at T2 — the T2 branch re-reads `posInfo.Volume()`, so 50% applies to what is left after T1, not the original size. Net: ~33% banked at T1, ~33.5% at T2, ~33.5% carried to T3, with the stop now ~2x the first target (1000 vs 500) rather than ~3x — the intended attack on the baseline's "avg win 0.55 vs avg loss 0.89." Targets stay ordered (500 < 1000 < 1800); `T2_Pips` equals `StopLoss_Pips` (1000), a symmetric risk-to-second-target.

### Dead protection functions now move real stops

This is the largest behavioral change. `ManageIndividualTrailing` previously walked positions and trailed only after T2; it now delegates to two helpers. `ApplyBreakevenToTickets(t1_tickets)` moves the real SL to the open price once a ticket has banked T1 and price is beyond entry — for a BUY only when `bid > op && sl < op`, for a SELL only when `ask < op && (sl == 0 || sl > op)`. The guards ensure breakeven only ever moves the stop toward profit and never past the current price, so it cannot move a stop the wrong way and cannot thrash (once `sl == op` the condition is false).

`ApplyTrailingToTickets(t2_tickets, Trail_Step_Pips)` then trails the real SL after T2 with the same monotonic guards the original inline code used (`newSL > sl && newSL > op` for BUY; `(sl == 0 || newSL < sl) && newSL < op` for SELL). When a ticket is in both `t1_tickets` and `t2_tickets`, breakeven runs first and trailing second; for a position past T2 the trailing SL sits above breakeven so the guards keep the two from fighting.

The concern is the *distance*, not the logic. `Trail_Step_Pips` is 30 and `Master_Trail_Step` is 15.0, both multiplied by `_Point`, so the live trailing stops sit 30 points ($0.30) and 15 points ($0.15) from price on XAUUSD. Those are far inside normal gold tick noise. Because these functions were dead in the baseline, the backtest that produced the -387.57 result never exercised them — so their real effect is entirely unobserved and is the most likely source of behavioral surprise (premature stop-outs) in the next run. If the intent was pip-scaled distance ($3.00 / $1.50), these should multiply by `pip` (point*10) instead of `_Point`.

### Master equity protection now modifies real stops

`CheckMasterEquityProtection` gains a call to `ApplyMasterTrailing(POSITION_TYPE_BUY/SELL, Master_Trail_Step)` inside the `masterBuyActive`/`masterSellActive` branches, so while a master trail is active it moves real broker stops in addition to the existing `CloseAllByType` basket safety net. `ApplyMasterTrailing` carries the same directional guards as the individual trail, so correctness is preserved. The subtlety is the metric it lives inside: `buyProfitPips`/`sellProfitPips` are *summed* over all same-side open positions in `CountOpenPositions`, not averaged or per-position. That aggregate only ever gated a close decision before; now it gates real stop movement too. With the new 2-position cap the sum is bounded, but two stacked positions at different entries will still produce a summed "profit pips" that does not correspond to either ticket's true distance from its stop. The per-ticket `PositionModify` in `ApplyMasterTrailing` itself uses each position's own `PriceOpen`/`BID`, so the modification is per-position correct; the risk is that the *trigger* to run it is derived from an aggregate. Worth confirming on the backtest that this does not tighten stops on a stacked pair in a way the old close-only path never did.

### Pattern reduction, version, and scope

Default-enabled patterns are trimmed to the six stronger signals (BullEngulf, MorningStar, ThreeWhite, BearEngulf, EveningStar, ThreeBlack); only the default literals changed, so any pattern can be re-enabled. Scope and consistency checks all hold: `grep 2.10` returns nothing (version bumped in header, `#property copyright`/`version`, both prints, and the dashboard title), braces/parens balance (172/172, 896/896), only `GaganEA.mq5` and `ITERATION_LOG.md` changed, and no new raw non-ASCII bytes were added (`\x25A0` is a pre-existing escaped literal). The log entry records all metrics as "pending next backtest" rather than fabricating results.

### Not tested

Nothing is machine-verified: there is no MQL5 compiler or MT5 in this sandbox, so compilation, the entry-throttle interaction, the reward:risk ladder, and — critically — the three newly-live stop-modification paths have never executed. The next MT5 Strategy Tester run on Windows is the authoritative check, and it should specifically watch for premature stop-outs from the 15/30-point trailing distances.
