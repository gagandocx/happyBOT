# Auto-tuner fix verification: delta-split, notuned rename, PF headroom guard (v2)

Second-pass review of the three fixes the implementer made after v1 returned NEEDS_CHANGES. Fix #2 (iteration-index reuse) and fix #3 (PF tiebreaker float headroom) are correct, complete, and introduce no regression. Fix #1 (surface the first-write StopLoss raise as a repair, not a nudge) is substantially in place and well documented, but its classification is coarse: when a diagnosis nudge and the ordering-repair touch the *same* param, the whole move is attributed to repair and the log/README assert it is "not a nudge" even though a nudge did target it. This is provably the case in the exact first-run scenario the fix documents.

Watch for: the first-write log line simultaneously carries `notes=... pf<1: tighten StopLoss ...` and `ordering/bounds repair (not a nudge): StopLoss_Pips`, with the full `StopLoss_Pips: [1000, 1800]` move in `repair_delta` and absent from `delta` (confirmed by dry-run against the real baseline). The two notes contradict on the surface and the "(not a nudge)" label is inaccurate for StopLoss in that case. Scoring/validation semantics are unchanged and the mq5 write is still always valid (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The PF-headroom fix is exactly right. Constants are untouched (offset 1e9, weight 1e-3), a `FLOAT-HEADROOM CONSTRAINT` comment documents the offset*2**-52 resolution reasoning, and `test_pf_tiebreaker_smallest_delta_headroom` pins two compliant candidates with identical net/trades and a 0.001 PF gap to strictly distinguishable scores. The guard has real teeth: the score delta at that gap is ~9.5e-7 against a float resolution of ~2.2e-7, so raising the offset or dropping the weight enough to collapse the tiebreaker makes `assertNotEqual` fail.

The iteration-index fix prevents the overwrite it targets. On a non-zero tuner exit the loop moves this cycle's `iterNNNN.html` and `.summary.json` to `iterNNNN_notuned_<IterStamp>` and commits those paths, so the next cycle (which reuses `iter(N+1)` because the counter did not bump) writes a fresh plain `iterNNNN.html` without clobbering the captured artifact. The rename is in a try/catch that falls back to the original name non-fatally, the Push-Location stack stays balanced (the rename block pushes nothing), the no-op-skip still fires only when nothing is staged, and the `_notuned` name sorts sanely under the pruner's descending-Name order (it sits just above its same-index plain sibling and never displaces a different index).

The delta-split fix is the one with a residual gap. It classifies a param as repair-origin iff `params.validate` changed its value between the pre-validate proposal and the post-validate vector, then routes that param's entire old-to-final delta into `repair_delta` and out of `delta`. That is correct when only repair touched the param, but when a nudge moved a param and repair then overrode it (StopLoss: pf<1 steps it 1000->900, ordering-repair raises 900->1800), the operator sees the whole 1000->1800 attributed to repair and an explicit "not a nudge" note, while a separate note in the same line says the pf<1 rule tightens StopLoss. The net final value and dominant origin are right; what is lost is that a diagnosis rule also targeted the param, and the wording overclaims.

### Delta-split classification: correct origin, wrong "not a nudge" claim on collisions

`propose_next` now returns `(valid, notes, repair_names)`, and `_ordering_repair_names(pre_validate, post_validate)` returns every param whose value `params.validate` changed. `tuner.run` then splits the old-to-new `delta` into `repair_delta` (keys in `repair_names`) and `nudge_delta` (the rest), logs them as separate `delta=`/`repair_delta=` fields, and appends the note `ordering/bounds repair (not a nudge): <names>`.

The classification predicate is "did validate move it," which is the right signal for a *pure* repair. The gap is that the split then hides the fact that a nudge also touched a repaired param. A dry-run against the real v2.11 baseline (`reports/round01_20260913.summary.json`: pf 0.58, DD 28.36, 1012 trades, which trips all three nudge rules) produces:

```
delta={"Entry_Cooldown_Bars": [3, 4], "Min_EMA_Distance": [400, 550],
       "Min_Trade_Distance": [500, 600], "Risk_Percent": [1.0, 0.75],
       "T1_Pips": [500, 450]}
repair_delta={"StopLoss_Pips": [1000, 1800]}
notes=... pf<1: tighten StopLoss, lower T1; coordinate-descent: step Min_EMA_Distance up;
       ordering/bounds repair (not a nudge): StopLoss_Pips
```

The `pf<1` rule ran `_step_down(v, "StopLoss_Pips", 2)` (1000 -> 900), then `_repair_ordering` raised StopLoss to 1800 to satisfy `T3=1800 <= StopLoss`. So StopLoss was intentionally nudged (down) and then overridden (up) by repair. The log tells the operator the 1000->1800 move is "not a nudge" while an adjacent note says the pf<1 rule tightens StopLoss, and the README section leans on the same claim ("This raise is a pure LEGALITY REPAIR, not a diagnosis-driven nudge"). The binary classification cannot express "nudge attempted, repair won," so the wording asserts the stronger, false claim that the nudge layer did not touch StopLoss. The written value (valid 1800) and scoring are unaffected; this is a transparency/accuracy defect in the operator-facing log and doc, in the one scenario the fix was built to clarify.

### PF tiebreaker headroom guard genuinely locks the interaction

`scoring.py` constants are unchanged (`TIER_A_OFFSET = 1e9`, `PF_TIEBREAK_WEIGHT = 1e-3`); the only addition is the `FLOAT-HEADROOM CONSTRAINT` comment spelling out that the tiebreaker product must stay above `offset * 2**-52`. `test_pf_tiebreaker_smallest_delta_headroom` scores two compliant candidates with identical net profit (1234.0) and trades (500) differing only in PF (1.500 vs 1.501) and asserts the higher-PF score is strictly greater and unequal. Measured, the two scores are `1000001234.0015000105` and `1000001234.0015009642`, a gap of ~9.5e-7 against a resolution of ~2.2e-7 at that magnitude, so the assertion has ~4x margin and would flip to equality (failing `assertNotEqual`) if a future edit raised the offset or shrank the weight enough to sink the product below the resolution. This is the exact regression guard v1 asked for.

### notuned rename prevents the overwrite and stays restart-safe

On `$tunerCode -ne 0`, the loop builds `iterNNNN_notuned_<IterStamp>` and `Move-Item -Force`s both the `.html` and `.summary.json` into it inside a try/catch, updating `$CommitReport`/`$CommitSummary` and `$CommitHtmlRel`/`$CommitSummaryRel` to the renamed paths (with a non-fatal fallback that keeps the original name and warns on rename failure). The git-add stage stages `$CommitHtmlRel`/`$CommitSummaryRel`, so a tuner-failed cycle commits the distinct `_notuned` artifact. Because the state counter is not bumped on failure, the next cycle recomputes the same `iter(N+1)` and writes a fresh plain `iterNNNN.html`, which no longer collides with anything committed. Restart-safety holds: the index is still read from the tracked `tuner_state.json` each cycle, and the already-committed `_notuned` file is unaffected by a restart.

The pruner filters `iter*.html` and sorts by `Name` descending. A `_notuned` name sorts just above its same-index plain sibling (`_` 0x5F > `.` 0x2E) and strictly below any higher zero-padded index, so it is neither wrongly pruned nor wrongly retained relative to real newer reports; retention by lexical name still tracks iteration order because the index is fixed-width. The Push-Location stack stays balanced: the rename and its try/catch push no location (they run inside the cycle-level try, after the tuner's own Push/Pop finally has already popped), and every other Push-Location in the cycle still pairs with a Pop-Location in a finally. The no-op-skip is intact: on failure the mq5, state, and current_params are unchanged but the new `_notuned` report is staged, so `git diff --cached` is non-empty and the cycle commits the captured artifact rather than skipping.

### Semantics unchanged and no signature breakage

`propose_next`'s return arity changed from 2 to 3; the sole caller in `tuner.run` unpacks the 3-tuple correctly and no test references the old shape. Verified: `py_compile` clean, tuner suite 34 green (up from 33, the +1 being the PF headroom test), analyzer suite 16 green, non-ASCII scan over the five touched files empty, `GaganEA.mq5` untouched.

### Test coverage of the new mechanism

The PF headroom path is now tested. The delta-split path is not: no test constructs the seeded-invalid vector and asserts which params land in `repair_names` versus `nudge_delta`, so the misclassification in issue 1 is invisible to CI. This is the coverage that would have surfaced the nudge-then-repaired StopLoss collision as an explicit expectation. As in v1, the entire PowerShell loop remains read-through only in this Linux sandbox (no MT5/compiler/PowerShell); the `_notuned` rename, commit-path rewiring, and pruner sort were verified by static reading and a name-sort simulation, not execution.
