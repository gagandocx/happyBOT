# Rule-based GaganEA auto-tuner and continuous backtest loop (v1)

A stdlib-only Python auto-tuner (`automation/tuner/`) plus a continuous PowerShell orchestration loop (`run_tuner_loop.ps1`/`.bat`) that grind GaganEA's 11 numeric `input` defaults toward a best risk-adjusted backtest score, one backtest at a time, keeping the best version seen. The scoring is a strict two-tier rule: maximize net profit under a hard 15% relative-drawdown ceiling, with any over-ceiling candidate always ranked below any compliant one. Parameter proposals come from coordinate descent plus rule-based nudges, are validated (clamp/snap/ordering-repair) so an invalid EA is never written, and are applied by a conservative per-line rewrite of the `input` literals. The loop compiles, backtests headlessly, analyzes, ingests, rewrites the next params, prunes old HTML, and commits per cycle. No trading-logic change to v2.11; the tuner tunes numbers only.

Watch for: the very first tuner write silently raises `StopLoss_Pips` from the live 1000 to 1800 as an ordering-repair side effect, bundled into the same commit as the nudges and never called out as distinct (confirmed). The README/ITERATION_LOG honesty caveats are accurate but do not mention this first-write behavior (confirmed). The whole loop and PowerShell are read-through only in this Linux sandbox (no MT5/compiler/PowerShell).

**Verdict**: NEEDS_CHANGES

## High-level view

The scoring rule is implemented correctly and defends its central guarantee. A large fixed offset (`TIER_A_OFFSET = 1e9`) lifts every compliant candidate above a separator while over-ceiling candidates sit at or below it, so a deeply losing but compliant candidate still outranks the best over-ceiling one, and missing drawdown is worst-cased into the over-ceiling tier. The one subtlety is float resolution: at 1e9 magnitude the PF tiebreaker (weight 1e-3) resolves to roughly 1e-6 per PF point, still above the ~1.2e-7 float epsilon there, so it works but with little headroom.

Parameter validation is robust. A 200k-iteration fuzz over out-of-bounds proposals produced zero invalid vectors; clamp/snap/ordering-repair always converges to `T1<T2<T3<=StopLoss` within bounds, including the adversarial case where the whole chain is pinned near the top and StopLoss cannot rise. The design deliberately seeds state with the RAW live vector (truthful) and only repairs at propose/write time, which means the first write mutates `StopLoss_Pips` 1000->1800 as a pure side effect of making the seeded-but-invalid v2.11 vector legal. That is sound in that the EA is only ever written a valid vector, but it is an unannounced 80%-wider stop applied on iteration 1 regardless of the backtest.

The rewriter is conservative and safe: exact word-boundary name matching (so `StopLoss_Pips_Extra` is never touched), value-only replacement preserving whitespace and trailing comments, byte-identical on same-value rewrite, int-vs-double literal formatting from the declared type, and a pre-write `MissingInputError` that prevents partial corruption.

The iteration index couples the loop and state through the tracked `tuner_state.json` counter, so `iterNNNN.html` maps 1:1 to the history record and survives restarts. The coupling is correct on the happy path and on first run (counter 0 -> iter0001). The gap is that a cycle which produces and commits a report but whose tuner call then fails leaves the counter un-bumped, so the next cycle reuses the same `iterNNNN` and overwrites that HTML and summary.

The continuous loop degrades gracefully: per-step failures log and `continue`, only a fatal config error exits, and every `Push-Location` is paired with a `Pop-Location` in a `finally` (plus a drain guard in the catch), so the location stack stays balanced across skips. The honesty caveats (numbers-not-logic, overfitting on the short window, local optimizer) match what the code actually does.

### Two-tier scoring and the tier-separation guarantee

The tier boundary holds at the extreme: a compliant candidate with net profit -500,000 scores ~9.995e8, while the best conceivable over-ceiling candidate (DD 15.0001, +1,000,000 profit, PF 3) scores ~ -1e-4, so the compliant-but-losing candidate wins. Missing drawdown is coerced to `_WORST_DD_PCT = 1e6`, landing a broken/partial report in Tier B where it can never masquerade as a winner.

The float-precision caveat is the one thing to watch. Adding `net_profit` and the PF term on top of the 1e9 offset means representable resolution near the score is ~1.2e-7; the PF tiebreaker contributes `1e-3 * PF`, so a PF gap of 0.001 between equal-net-profit candidates still resolves (delta ~1e-6) but with only about an order of magnitude of headroom. Any later increase of `TIER_A_OFFSET` or decrease of `PF_TIEBREAK_WEIGHT` could silently erase the tiebreaker, and no test pins this interaction; `test_pf_tiebreaker` should assert distinguishability at the smallest meaningful PF delta.

### Ordering repair and the seeded-invalid v2.11 vector

A 200,000-iteration fuzz feeding values 500 points outside each bound produced zero `is_valid` failures, including the adversarial pin `{T1..T3 at chain top, StopLoss=400}` where clamping fights ordering: the repair still resolves to a strictly increasing chain under the cap. It cannot emit an invalid vector.

The consequential design choice sits at the seam between `state.init_from_mq5` and `validate`. The shipped v2.11 EA has `T3_Pips=1800 > StopLoss_Pips=1000`, which violates the spec ordering. The implementer records the raw live values in state (honest) and repairs only at propose/write time. The consequence, confirmed by a dry run against a representative summary: the first real tuner write emits `StopLoss_Pips: [1000, 1800]` in the delta. So the tuner's opening move widens the stop by 80% purely to make the seeded vector legal, on top of the diagnosis-driven nudges (cut risk, widen distances, lower T1). This is architecturally sound (the EA is only ever written a valid vector) and the state file remains truthful, but the risk-profile change is neither diagnosis-driven nor flagged: in the log delta it is indistinguishable from an intentional nudge, and the README does not mention it. Either raise StopLoss lazily with an explicit note, or surface repair-origin deltas separately, so an operator eyeballing the first iteration is not surprised by a materially different stop.

### mq5 rewriter safety

Verified directly against an adversarial block: rewriting `Risk_Percent` and `StopLoss_Pips` where the file also contains `StopLoss_Pips_Extra` leaves the substring-name line untouched (word-boundary escape works), preserves comment alignment, is byte-identical on a same-value rewrite, and emits doubles with a decimal point (`1.0`, not `1`) so the recompile stays clean. A missing requested name raises `MissingInputError` from `rewrite_text` before `rewrite_file` opens the file for write, so a bad update set can never leave a half-rewritten file. No corruption path found; this is the most defensively built part of the change.

### Restart-safe state, atomicity, and the iteration index

The history record's `params` are `state["current"]` captured before the propose step overwrites current with the new vector, so `iterNNNN.html` genuinely maps to the params that produced it, confirming the 1:1 mapping the docs claim.

The coupling has one hole. The counter only advances when the tuner both succeeds and persists state (`state_mod.save` runs after a successful rewrite; the `MissingInputError` path returns before saving, so the bumped counter is discarded). The loop, however, copies the report and runs the analyzer in earlier steps and then commits `iterNNNN.html` + summary even when the tuner call exits non-zero ("Committing this cycle's report anyway"). In that case the counter stays at N, so the next cycle recomputes `iter(N+1)` and overwrites the just-committed HTML and summary. The committed history stays consistent (no record was written for the failed ingest), but the on-disk artifact for that index is silently replaced. Decoupling the report index from tuner success, or giving a tuner-failed cycle a distinct report name, would remove the overwrite.

### Continuous loop failure handling and location-stack balance

On the three questions the briefing raised, the loop holds up. All five `Push-Location` sites pair with a `Pop-Location` in a `finally`, and since a `continue` inside a `try` runs the `finally` first, no skip path leaks a pushed location; the catch adds a bounded drain loop as a net, so the stack cannot go unbalanced. Report discovery compares `LastWriteTime` against the run start and warns/skips when a matched report predates the launch, so a failed tester run does not commit a stale report as fresh. And per-step failures uniformly log and `continue` with only the pre-loop config check calling `Fail`, so one bad backtest cannot wedge the grind. Compile success is judged by parsing the log for a `(line,col) : error` marker and an `N error(s)` count rather than the unreliable MetaEditor exit code.

### Honesty of the caveats

The README and the ITERATION_LOG Round 3 entry state three things and the code backs each: it optimizes numbers not logic (the rewriter only touches `input` default literals, no strategy code), it will overfit on the short window (`backtest_template.ini` uses the ~1-month window and the caveat tells the operator to re-validate the best on the full 6-month window), and it is a local optimizer (coordinate descent + rule nudges with keep-best, which is a hill-climb). The PF 0.58 / below-1 claim is consistent with the prior round and is used to justify "tuning cannot create an edge." No invented performance numbers appear in the Round 3 entry (metrics are marked pending). The only omission is the first-write StopLoss behavior noted above.

### Test coverage

33 unittest cases pass (scoring, params, rewriter, state); the scoring tests directly assert the tier-separation guarantee (over-ceiling below worst compliant, none-DD treated as over-ceiling, overage ordering), the low-trade penalty, worst-casing, and a PF tiebreak. params tests cover clamp/snap/type/ordering; rewriter tests cover comment preservation, substring safety, and missing-name; state tests cover atomic write, best-on-improvement, delta, and init-on-corrupt. Not tested: the composed `propose_next` -> `validate` -> `rewrite_file` path that produces the first-write StopLoss jump (would catch the undocumented side effect as an explicit expectation); the PF tiebreaker at the smallest meaningful delta against the 1e9 offset (float-headroom regression guard); and, unavoidably in this environment, the entire PowerShell loop, compile-log parsing, and report-discovery logic, which are read-through only and rest on the first manual Windows run.
