# In-sandbox stdlib tick backtester and research loop for GaganEA (v1)

Adds `python_bt/`, a pure-Python, stdlib-only tick backtester so XAUUSD strategies can be developed and ranked inside the sandbox without an MT5 round-trip, plus `data/extract.py` to regenerate the gitignored 526 MB tick CSV from tracked split-zip chunks. The stack streams ticks, aggregates M5 bars, simulates a hedging broker with spread fills / commission / SL-TP / tiered partials / breakeven / trailing, ports GaganEA v2.12's entry-exit core, emits metrics in the existing analyzer schema, and ranks candidates through the *same* `automation/tuner/scoring.py::score()` that enforces the hard 15% relative-DD ceiling. `research.py` is the loop the user asked for: batch configs → replay → rank → leaderboard + per-config diagnosis → persisted results JSON to read back and iterate. GaganEA.mq5 is untouched, all source is pure ASCII, and the full suite (71 python_bt + 16 tools + 38 tuner tests) passes.

Watch for: (1) **confirmed** — `--to YYYY.MM.DD` on the runner/research CLI slices to *midnight* of that day, silently dropping the entire end day; (2) **confirmed** — every P&L/margin constant in `config.py` is an unverifiable parity assumption (flagged CONFIRM), so absolute money figures are only trustworthy after MT5 confirmation; (3) **likely** — the H1-EMA200 needs ~200 hours of stream to warm up, so short slices produce zero trades with no warning, which can read as "strategy is flat" rather than "not warmed up".

**Verdict**: APPROVED

## High-level view

The design deliberately mirrors the existing MT5 toolchain instead of inventing a parallel one: metrics.py produces the exact key names `analyze_report.py` and `scoring.py` already read, and both scoring and the diagnosis vocabulary are *imported* (via sys.path bridges) rather than reimplemented, so a Python leaderboard and an MT5 report speak the same language and the 15% ceiling is enforced in one place. Ranking correctness rests entirely on that reuse, and the canned-row tests confirm an over-ceiling config always sinks below any compliant one.

The broker is the correctness core and is modeled carefully: buy-at-ask / sell-at-bid, commission per lot per side on open and each partial close, SL/TP firing on the closing-side quote cross (SL checked before TP as a conservative gap rule), proportional partial P&L, and O(open-positions) per-quote drawdown tracking. The money formula `profit_price / TICK_SIZE * TICK_VALUE * lots` is applied consistently everywhere P&L is computed.

The GaganEA port is honest about being faithful-not-byte-exact: it reproduces the trend/distance/session/ATR-regime/pullback-RSI-confluence entry stack and the ATR dynamic SL/TP + scaled-tier exit stack with breakeven and trailing, and matches the EA's quirk of sizing lots off the fixed `StopLoss_Pips` even when the ATR SL is active. The documented approximations (bar-close timing, SMA indicator seeding, H1 EMA built from M5 mids, mid-based price basis) are real and clearly stated.

The gating strategy is sound: parity assumptions live in one config module flagged CONFIRM, and the whole rig is repeatedly documented as a fast *search* stage with MT5 remaining the source of truth. The known gaps are the CLI `--to` day-truncation, the silent warm-up-vs-flat ambiguity, and bar-mode SL/TP being checked only at each bar's closing quote (documented).

1. **`--to` drops the end day** — `iter_ticks` coerces a `YYYY.MM.DD` `date_to` string to midnight, so `--to 2026.09.01` keeps only `00:00:00.000` of Sep 1 and discards the rest of the day. Either interpret a bare date `date_to` as end-of-day, or document that `--to` is exclusive of the named day.
2. **Config constants are unverified parity assumptions** — `POINT_SIZE/TICK_SIZE/TICK_VALUE/CONTRACT_SIZE/COMMISSION/INITIAL_DEPOSIT/LEVERAGE` are guesses flagged CONFIRM; a wrong value silently biases all money/lot/DD figures. Confirm against the Fusion Markets symbol spec before trusting absolute P&L (relative ranking is unaffected).
3. **Warm-up reads as a flat strategy** — H1-EMA200 needs ~200 hourly closes before any entry can fire, so short slices yield zero trades and a misleading "NOT SUITABLE / net 0" verdict. Surface a warm-up / insufficient-data note when no entry ever became eligible.
4. **Bar-mode intrabar fills approximated** — in bar mode SL/TP and tier hits are evaluated only at each bar's closing quote, and an SL modified inside `on_bar` fires no earlier than the next bar. Documented; use tick mode when fill accuracy matters.

### Scoring and metrics reuse, not reimplementation

`scoring_bridge.py` and the diagnosis import in `runner.py` put `automation/tuner` and `tools` on `sys.path` and re-export `score()`, `build_diagnosis()`, `diagnosis_verdict()` rather than duplicating them, so the hard 15% ceiling and its tier-separation math live in one place. `metrics.py` returns `total_net_profit`, `relative_drawdown_pct`, `profit_factor`, `total_trades` — exactly the keys `score()` reads — plus the fuller schema matching `reports/samples/sample_report.summary.json`. The canned-row ranking tests (`test_over_ceiling_config_ranks_last`, `test_full_ordering`) pin the guarantee that a compliant-but-losing config outranks a rich-but-over-ceiling one.

Cross-path comparison nuance: the Python `relative_drawdown_pct` is the largest per-quote peak-to-trough equity *percent* decline — the intended MT5 "relative drawdown" analog, but computed on this engine's mid-based equity curve, so it is comparable in *meaning*, not guaranteed equal to MT5's figure to the decimal.

### Broker P&L, commission, and drawdown

Commission is charged on open and on every close including partials (`_commission = COMMISSION_PER_LOT_PER_SIDE * volume`), so a scaled-out position pays commission proportional to each tranche — matching MT5 deal accounting. SL is checked before TP on each side, conservatively resolving a bar that gaps through both to the stop. `rel_drawdown_pct`/`rel_drawdown_money` track the drop that produced the largest *percent* decline from its peak (the value scoring reads); `absolute_drawdown` is deposit-minus-lowest-equity-below-deposit. The scripted `test_scripted_peak_to_trough_drawdown` hand-verifies these against a two-quote sequence, and the partial/hedging/breakeven tests compute expected net profit by hand rather than asserting on recomputed values — genuine coverage, not tautologies.

### GaganEA v2.12 port fidelity

Cross-checked against `GaganEA.mq5`. Two easy-to-miss details are correct: both T1 and T2 close a percent of *current* volume (the EA re-reads `posInfo.Volume()` before T2, and `_tier_close_volume` mirrors the `closeLots >= lots -> lots - minLot` clamp), and `CalcLotSize` (~712) sizes lots off `StopLoss_Pips * _Point` regardless of the active ATR SL — `_enter` replicates this by passing the fixed StopLoss distance to `_calc_lot_size`. The entry stack (HTF+CTF EMA200 trend, `Min_EMA_Distance`, concurrent cap, cooldown, session, ATR regime, pullback-resume + entry-RSI confluence, `Min_Trade_Distance`) maps gate-for-gate, with a dedicated rejection test per gate.

The legacy pattern-entry branch is intentionally not ported (`buy_ok = False` when `Use_Confluence_Entry` is off) and the Round-4 optional subsystems are explicitly listed as omitted. The documented approximations are real and honestly stated: entries decided on the just-*closed* bar (the EA reads the forming bar's buffer index 0), SMA indicator seeding, H1 EMA200 sampled from the last M5 mid close of each hour rather than a broker H1 series, and mid-based trend comparisons while fills use real bid/ask.

### Loader streaming and the `--to` slice

`iter_ticks` is a true generator (line-by-line, no full-file read) that stops early once a tick passes `date_to`. The sharp edge: `_coerce_bound` turns a `YYYY.MM.DD` *string* `date_to` into that day at `00:00:00`, so the CLI's `--to 2026.09.01` keeps only the first instant of Sep 1 and drops the rest. The loader tests only exercise `date_to` as an end-of-day *datetime*, so this passes tests while the CLI string path silently truncates the final day. Either treat a bare-date `date_to` as end-of-day or document it as exclusive.

### Research loop delivers the user's ask

`research.py` implements the DEVELOP -> MEASURE -> RANK -> ITERATE loop the user requested: it replays each config through the *same* `run_once` the runner uses, ranks by score descending (None scores sink last), prints a leaderboard with net profit / relDD% / PF / trades / score / diagnosis, and writes a small timestamped `reports/pybt/<ts>.results.json` the agent reads back to form the next hypothesis. The results path is deliberately `*.results.json` under `reports/pybt/` so it escapes the `reports/*.summary.json` gitignore rule (which matches direct children only) — verified.

Practical caveat confirmed by running the harness: on random or short data the H1-EMA200 warm-up (~200 hours) plus confluence gating means zero entries fire, which the leaderboard renders as net 0 / "NOT SUITABLE" rather than "not enough data to warm up." On the real 2-month window (~1500 hours) the H1 EMA warms fine, so this is a smoke-run/usability sharp edge, not a correctness bug — but a warm-up note would prevent misreading a flat result as a losing strategy.

### Data extraction, ASCII, and repo hygiene

`data/extract.py` reassembles the five tracked `*.zip.001..005` chunks (verified present) and unwraps the two-level nested zip with stdlib `zipfile`, streaming in 1 MB buffers, idempotent unless `--force`. `.gitignore` ignores `data/joined.bin`, `data/*.zip`, `data/**/*.csv`, `data/*.csv`, so neither the reassembled archive nor the 526 MB CSV can be committed while the chunks stay tracked. Source files are pure ASCII (only compiled `.pyc` artifacts contain non-ASCII, and `*.py[cod]` is gitignored). GaganEA.mq5 shows no diff.
